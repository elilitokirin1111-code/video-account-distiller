# 产品方向与开发路线

## 产品定位

Video Account Distiller 的目标不是成为通用爬虫，而是一个“可审计的视频账号研究工作台”：
把用户授权的导出数据或公开主页数据转成不可变证据、标准化数据、账号体检、内容分析、
对标结论和可复用实验建议。

产品由三层组成：

1. 稳定分析内核：导入、校验、Parquet/DuckDB、指标、抽样、报告、蒸馏和发布复盘。
2. 易用工作台：FastAPI 提供统一能力边界，Streamlit 提供初始化、采集、导入、分析和报告浏览。
3. 可插拔数据源：TikHub 是标准公开主页入口；MediaCrawler 是显式可选的本地研究适配器；
   授权导出、飞书和 Google Sheets 继续走既有官方/授权边界。
4. 可选知识层：Distiller 生成受控、脱敏、带证据反链的知识文档；OpenKB 只作为独立
   Sidecar 编译和检索这些派生成果，不读取原始证据，也不反向改写规则。

## 当前基线

- Phase 0～7 的离线分析内核和 1.0.0 安装包链路已完成。
- Phase 8 已具备 TikHub、MediaCrawler、评论采样、本地 Whisper/Ollama 媒体增强和账号画像。
- CLI、API 和 Web 已合并到同一集成线；默认契约统一为 TikHub、20 条作品、0 条评论。
- 全主页、评论采集、MediaCrawler 浏览器和本地媒体下载都必须显式启用。
- API 异步任务已收口为 SQLite 持久契约；重启中断任务会标记为可重试失败。
- 采集已具备 `standard`、`comprehensive`、`owned` 三档、调用预算、能力矩阵和实际覆盖率。
- 重复账号快照可计算粉丝、获赞、作品数等观察期增长。
- GPT/外部工作流可从单一受限上下文 API 读取证据、缺口与分析合同。
- OpenKB 已通过 `knowledge-outbox/openkb/`、CLI 和 API 接入，具备显式模型确认、
  内容哈希幂等、同目标版本替换、脱敏和项目完整性校验。

## 不变的产品合同

- 默认操作必须有限、可预演、可解释；付费调用必须显式确认。
- Provider 原始响应先形成不可变证据，再进入统一分析内核。
- 缺失的公开指标保持未知，不写成 0，不制造跨平台可比性。
- 凭证只来自环境变量；浏览器会话、密钥和授权头不进入项目或 Git。
- MediaCrawler 不进入根项目 wheel，不改变其第三方许可边界。
- 模型不可用时可以明确降级，但不能伪造视觉、语义或因果结论。

完成条件：Provider 故障只影响采集层，不破坏已保存证据和分析项目。

- 由维护者明确决定版本号、标签和发布窗口。

## 当前不做

- 后台持续爬取、代理池、隐身、自动登录或验证码绕过。
- 默认全主页或默认评论采集。
- 把 MediaCrawler 第三方源码打进 wheel。
- 自动把相关性写成因果性，或让低成熟度规则自动升级。
- 让 OpenKB 读取 `raw/`、`normalized/`、评论明文、媒体、浏览器会话或凭据，或把
  OpenKB 回答当作权威事实写回 Rule/Rubric。
